# Генеративный интерфейс Киры, v1

Клиент может разрешить необязательный виджет на один ход. Ответ по-прежнему содержит самодостаточный текст для чата и озвучки. По умолчанию виджеты выключены; название устройства, слова пользователя и прежний ход их не включают. Telegram продолжает пользоваться своим транспортом.

## Выбор стандарта

Проверено 2026-11-08: [A2UI v1.0](https://a2ui.org/specification/v1.0-a2ui/) описывает декларативные поверхности, каталоги компонентов, события и независимый от транспорта обмен. Его `createSurface` позволяет передать начальные компоненты одним сообщением. Это подходит для текущего REST API.

[Adaptive Cards](https://learn.microsoft.com/en-us/adaptive-cards/rendering-cards/implement-a-renderer) также поддерживает нативные карточки и действия. Здесь выбран A2UI с собственным ограниченным каталогом: можно расширять состав визуализаций, сохраняя общий envelope и нативный рендеринг. Это инженерный выбор проекта, а не заявление, что один стандарт лучше для всех приложений.

Контракт Киры — **ограниченный профиль A2UI 1.0**, а не реализация всех возможностей стандарта. Каталог `urn:kira:ui:catalog:1` определён типами в `generative-ui/contracts.ts` и [JSON Schema](generative-ui.schema.json). Это идентификатор, его не нужно загружать из сети. Каталог содержит собственные свойства компонентов; один стандартный A2UI basic renderer без регистрации этого каталога недостаточен.

## Запрос и ответ

В `POST /api/v1/messages`, `/photos`, `/actions` и исполняемый `/scene/turns` добавляется:

```json
{
  "text": "Сравни два варианта плана",
  "ui": { "enabled": true, "catalogId": "urn:kira:ui:catalog:1" }
}
```

Остальные поля, Bearer и `Idempotency-Key` соответствуют существующему маршруту. Для `/actions` вместо `text` передаётся `actionToken`; для фото/AR сохраняются их обязательные поля. Без `ui` или с `ui: {"enabled":false}` визуальная генерация не вызывается. Неизвестный каталог/лишние поля отвергаются до выполнения. `GET /capabilities` возвращает `generativeUi` с версией, каталогом, лимитами и списками компонентов/действий.

У одного текстового сообщения в обычном `messages[]` может появиться `ui`:

```json
{
  "messages": [{
    "id": -1001,
    "type": "text",
    "format": "plain",
    "text": "Предлагаю чтение на 20 минут и прогулку на 30 минут.",
    "ui": {
      "protocol": "a2ui",
      "version": "1.0",
      "catalogId": "urn:kira:ui:catalog:1",
      "messages": [{
        "version": "1.0",
        "createSurface": {
          "surfaceId": "kira_11111111111141118111111111111111",
          "catalogId": "urn:kira:ui:catalog:1",
          "components": [
            {"id":"root","component":"Card","child":"plan"},
            {"id":"plan","component":"Column","children":["heading","items"]},
            {"id":"heading","component":"Text","text":"Вечер","variant":"title"},
            {"id":"items","component":"Table","columns":["Занятие","Минуты"],"rows":[["Чтение","20"],["Прогулка","30"]]}
          ]
        }
      }]
    }
  }]
}
```

Виджет необязателен даже при opt-in. Модель выбирает его уместность по готовому ответу; приветствия, поддержка, ошибки и отсутствие данных обычно остаются текстовыми. Клиент всегда умеет показать и озвучить `text` без схемы.

## Каталог

Все значения литеральные. `id` — ASCII-идентификатор до 48 символов, корневой компонент имеет `id=root`. Другие компоненты связаны ссылками `child`/`children`; это одно дерево без циклов, повторных родителей и недостижимых узлов.

| Компонент | Поля помимо `id`, `component` | Нативное представление |
|---|---|---|
| Column, Row | `children: string[]`, `gap?: small/medium/large` | Стек; Row переносится на узком экране |
| Card | `child: string` | Карточка с отступами и фоном/обводкой приложения |
| Text | `text: string`, `variant?: title/body/caption` | Обычный текст, без HTML/Markdown |
| Divider | — | Разделитель |
| Metric | `label`, `value`, `detail?`, `tone?: neutral/positive/negative` | Показатель с подписью и пояснением |
| Table | `columns: string[]`, `rows: string[][]` | Таблица или доступные карточки строк |
| Chart | `kind: line/bar/donut`, `labels: string[]`, `series: [{label,values:number[]}]`, `unit?` | Нативный график и доступное текстовое представление данных |
| Button | `child: string`, `action` | Нативная кнопка; child обязательно Text |

Полные ограничения полей — в JSON Schema. Общие пределы: 32 КиБ UTF-8, 64 компонента, глубина 8, 6 кнопок; до 16 детей контейнера, 6 колонок/24 строк таблицы, 4 рядов/48 точек графика. Длины рядов и подписей совпадают; donut имеет один неотрицательный ненулевой ряд. Цвета, размеры шрифтов, радиусы и адаптация задаются темой устройства. Значение `tone` не заменяет текстовую подпись.

В v1 отсутствуют формы, привязки `@path`, выражения `@call` в свойствах, загрузка изображений, произвольные функции, WebView, код, incremental updates и фоновые изменения поверхности. Единственное разрешённое `@call` — `openUrl` внутри нажатия Button.

## Действия

`Button.action` имеет один из двух A2UI-видов:

```json
{"functionCall":{"@call":"openUrl","args":{"url":"https://example.org/details"}}}
```

Клиент по явному нажатию открывает HTTPS-ссылку штатным способом. Сервер разрешает только точную ссылку из ответа или уже существующей кнопки, без credentials. Автоматическое открытие и выполнение на mount запрещены.

```json
{"event":{"name":"kira.reply","context":{"actionToken":"OPAQUE_SERVER_TOKEN"}}}
```

Для `kira.reply` и `kira.action` клиент отправляет **только непрозрачный токен** существующему `POST /actions` с новым `Idempotency-Key` и, если нужен следующий виджет, новым opt-in `ui`. A2UI `surfaceId`, `sourceComponentId`, `timestamp` могут использоваться клиентом локально, но произвольный A2UI event/body этот endpoint не принимает.

- `kira.reply` — подписанная сервером новая пользовательская реплика: «Покажи завтра», «Да, хочу подробнее», «Нет, оставь как есть». Она проходит тот же text handler, intent, источники и подтверждения, что введённый текст; привилегия внешней отправки ей не выдаётся.
- `kira.action` — **уже существующий** signed token кнопки обычного ответа, например подтверждения подготовленного действия. Модель выбирает только индекс разрешённой кнопки; не создаёт callback, инструмент, endpoint или токен.
- Токены связаны с владельцем, сообщением, версией текущего API-хода и сроком 15 минут. После нового хода прежние кнопки устаревают. Доменный callback сохраняет свои дополнительные проверки. Повтор одного токена под новым ключом воспроизводит квитанцию без повторного действия; изменение UI-предпочтения у уже использованного токена может вернуть конфликт.
- `action_expired` означает предложить заново запросить карточку. После неопределённого исхода сохраняется прежний запрет автоматического повтора с новым ключом.

Схема не доказывает, что действие выполнено. До нажатия и успешной серверной квитанции ничего не происходит. «Да/нет» не являются универсальным подтверждением чужого pending-state: для подготовленного действия нужно использовать его существующую кнопку.

## Серверный путь и ограничения v1

1. Канонический обработчик выполняет задачу и формирует текст/обычные кнопки/файлы.
2. При явном opt-in отдельный read-only compositor получает текущую просьбу, **готовый текст**, подписи уже выданных кнопок и ссылки. Он не получает исходные фото, память, секреты, схемы инструментов или сырые callback-и и не вызывает инструменты.
3. Один логический вызов задачи `conversation` под preset приложения возвращает компоненты или null. Общая provider policy, согласие и квота продолжают действовать. Это добавляет задержку и расход AI при opt-in; ускорение не заявляется. Отдельного classifier-а и JSON-repair для UI нет; технические retry/fallback общего AI-транспорта сохраняются.
4. Сервер проверяет allowlist, поля, дерево, размеры и действия, назначает surfaceId и привязывает токены. Некорректная схема/ошибка optional-генерации оставляет уже готовый текст и результаты действий.
5. Snapshot попадает в обычную durable API-квитанцию и в presentation metadata истории. При повторе запроса возвращается тот же surfaceId/токены без новой генерации.

Компонозитор видит только итоговый текст: он не должен строить исторический график, если в ответе нет точек. Числа/факты остаются результатом модели: структурная валидация не доказывает их истинность. Источники, даты, единицы и неопределённость должны сохраняться в виджете; свежие данные добывает прежний основной pipeline. Для больших данных нужен будущий типизированный evidence/data binding, без копирования массивов через модель.

В v1 выбирается последнее новое plain-text сообщение; HTML-системные карточки, edits, media и notice не преобразуются. Text+voice сохраняют прежний контракт. При включённом UI `Prefer: respond-async` не применяется: сервер возвращает завершённый синхронный ответ, без `Preference-Applied`. Фоновые `/dialogue-jobs` не меняют уже созданные поверхности. В истории сохраняются последние 20 UI-snapshot-ов в пределах имеющегося текстового history retention; старые сообщения продолжают иметь текст.

Для AR применяется тот же snapshot как 2D-панель, закреплённая **клиентом**. Каталог не даёт координат комнаты и не управляет телом Киры; это остаётся в существующем `/scene/turns` action-контракте. Пространственные компоненты/формы/streaming требуют отдельной версии каталога и capability negotiation, а не необязательных полей, которые старый клиент не понимает.

## Проверки

`npm run test:unit -- tests/generative-ui.test.ts tests/external-api-generative-ui.test.ts tests/external-api-scene-runtime.test.ts` проверяет протокол, schema, HTTP→handler→widget→action, повторы, истечение версии, историю, фото и AR.

`npm run eval:generative-ui -- --live` в настроенном диагностическом runtime проверяет реальные решения модели на вымышленных прогнозах/ценах/планах, вариантах формулировок, поддержке, отсутствии данных и injection в источнике. Прогон не читает память/Telegram и не выполняет бизнес-мутации; обычная AI usage telemetry сохраняет прежнее поведение. Он дополняет offline-тесты, но не запускается автоматически в `npm test`.
