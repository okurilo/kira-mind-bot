# Генеративные виджеты Telegram

Telegram Bot API 10.4 от 9 ноября 2026 позволяет боту отправлять HTML-виджеты непосредственно в личный чат. Используем [официальный Widget profile 1](https://core.telegram.org/bots/widgets) и [sendWidget / widget_query](https://core.telegram.org/bots/api#sendwidget). В production пока доступны только личные чаты с ботом; группы, inline mode, forwarding и shared widgets не включаем.

## Как это работает

1. Обычный обработчик Киры получает сообщение, выполняет инструменты и формирует канонический ответ. При доступной карточке текст остаётся естественной короткой репликой для чтения и озвучки: без ASCII-интерфейса, Markdown-таблиц и технических подписей.
2. При включённом `KIRA_TELEGRAM_WIDGETS_ENABLED` один необязательный вызов общего compositor решает, нужен ли виджет, и создаёт проверенный A2UI snapshot [каталога v2](generative-ui-v2.md). Приветствия, поддержка и отсутствие данных обычно остаются текстом. Инструменты и память этому вызову недоступны.
3. Серверный renderer компилирует схему в собственный HTML/CSS/SVG и фиксированный JS. Модель никогда не поставляет исполняемый код. Короткий обычный ответ до 1024 символов отправляется **одним** widget-сообщением: весь текст становится caption, отдельного дубля и цитаты предыдущего ответа нет. Клиент с поддержкой показывает карточку с подписью, клиент без renderer сохраняет читаемую подпись. Голос, файлы, готовые системные блоки и длинный текст сохраняют основной транспорт; дополнительная карточка не получает служебную подпись. Явный отказ Telegram возвращает обычный текст, неопределённая доставка виджета не повторяется. Сбой записи UI после успешного send не вызывает второй ответ.
4. Кнопка внутри виджета вызывает `TelegramWidget.request()`. Сервер подтверждает запрос до запуска AI и пропускает ответ/форму через тот же text handler, а подтверждение действия — через существующий callback router с исходным сообщением, клавиатурой и сессией Telegram. API-диалог и его action tokens в этом пути не участвуют.

Исходные legacy-клавиатуры подтверждений остаются на обычном текстовом сообщении: их обработчики могут редактировать этот текст, что несовместимо с заменой на media-caption. Сгенерированные быстрые ответы и формы не требуют такой клавиатуры и поддерживают доставку одной карточкой.

В Telegram возможность задаёт сам транспорт: виджеты включены по умолчанию для личного диалога владельца. Аварийный выключатель `KIRA_TELEGRAM_WIDGETS_ENABLED=false` передаётся также tenant-workers. Для API приложения по-прежнему обязательно явное request-local `ui.enabled`; флаг Telegram не меняет API opt-in.

## Компоненты и ограничения поверхности

Схема общая с мобильным приложением: `Column`, `Row`, `Card`, `Text`, `Divider`, `Metric`, `Table`, `Chart`, `Button`, `Progress`, `Steps`, `Map`, `Image`, `Countdown`, `Checklist`, `Choice`, `Slider`, `Toggle`, `DateTime`.

- Компоновка предпочитает крупные показатели и небольшие блоки; Row с двумя короткими Metric сохраняет горизонтальную раскладку и переносится на узком экране. Длинные таблицы и подписи переходят на страницы; шапка таблицы повторяется только на новой странице, стрелки скрыты при одной странице. Пустой статус места не занимает. Графики line/bar/donut рисуются локальным SVG и сопровождаются точными значениями. Цвета берутся из темы Telegram.
- Нет доступа к сети, внешним картинкам и картографическим тайлам. `Map` показывает подтверждённые координаты и кнопку открытия карты; `Image` показывает alt, сами файлы остаются обычными вложениями. Countdown считает оставшееся время на устройстве, сохраняя исходный UTC deadline.
- Telegram удаляет input/select/textarea и не даёт клавиатуру. Choice и Toggle используют кнопки, Slider — шаги, DateTime — шаг 15 минут в допустимом диапазоне. Время берётся из значения/границы схемы; если отправная дата отсутствует, карточка не отправляется. Заполненная форма становится обычной текстовой репликой с видимыми значениями; подтверждения внешних действий сохраняются.
- Перед отправкой проверяем исходный A2UI snapshot и размер: HTML до 32768 UTF-8 байтов, zlib level 9 до 3800 байтов с запасом к пределу Telegram 4096. До 100 небольших блоков; страницы целятся в 430 px содержимого, с навигацией ниже 560 px. Ссылки не длиннее 256 символов. Слишком большой/неподдержанный snapshot, отказ модели или Telegram оставляют уже доставленный основной ответ. Отправка виджета не повторяется после неопределённой ошибки транспорта.
- `chat_data` и ответ на query используют компактные индексы полей и ревизию, укладываются в 1024 байта. Код и макет после отправки неизменяемы. Изменение формы обновляет только presentation state, без AI, инструментов и новых записей диалога. Пассивное обновление избранного/AR остаётся отдельным [API-контрактом](widget-refresh.md); Telegram-карточка показывает snapshot с его временем, новый вопрос создаёт новый snapshot.

## Действия и сохранение

В `bot_settings` хранится отдельное Telegram presentation namespace, связанное с владельцем, точным `message_id` виджета, исходным ответом, каноническим маркером Telegram-хода и сроком 15 минут. Блокировка диалога берётся раньше блокировки UI, как в API; каналы изолированы. После перезапуска остаются выбранные поля и квитанция действия. Храним не больше 128 карточек на владельца.

Wire data имеет вид `f:<revision>:<field-index>:<numeric-value>` или `a:<revision>:<action-index>`, до 64 UTF-8 байтов. Choice передаёт индекс варианта, Slider — номер шага, Toggle — 0/1, DateTime — миллисекунды UTC. Сервер сверяет определение и диапазон, а форму повторно проверяет общим `submissionText`. Скрытый/неиспользованный action index не принимается. Произвольный текст callback или аргументы инструментов от виджета не принимаются.

Действие атомарно получает durable receipt перед ответом Telegram. Один виджет передаёт не больше одного действия/отправки формы; повторный клик и повторная доставка update возвращают состояние без исполнения. При потере подтверждения исполнения автоматически не повторяем. Более новый ход делает старые действия недоступными; запоздалый compositor проверяет маркер ещё раз непосредственно перед send. Открытие ссылки остаётся локальным действием пользователя.

Query принимается только от владельца в исходном private chat, без inline/shared/wallet authority. `widget_query` включён в `allowed_updates` в обоих режимах запуска. Узкий raw API adapter использует существующие HTTP transport/transformers grammY, даже если установленные типы ещё не знают Bot API 10.4. Bridge стоит перед session middleware и восстанавливает каноническое событие только после проверки и квитанции. Callback acknowledgement не отправляется повторно как `answerCallbackQuery`.

Текст прежнего callback toast сохраняется как статус карточки через `chat_data`; его нельзя отправить вторым ACK уже подтверждённого query. Это сохраняет сообщения об успехе, отказе или устаревшем подтверждении. Квитанция сама по себе означает принятие запроса, а не успешное выполнение действия.

Telegram не сообщает боту, пришёл ли query от нажатия или из фона. Поэтому доверенный JS никогда не запрашивает действия при появлении карточки или по таймеру; только синхронно внутри обработчика кнопки. Таймер Countdown не обращается к серверу. Блокировки PostgreSQL и сетевые вызовы ограничены по времени, чтобы успеть подтвердить query в пределах 15 секунд.

## Проверки и примеры

Автоматические проверки: обычный Telegram text handler → ответ → sendWidget → widget_query → следующий обычный ход; существующий callback с исходным контекстом; deferred ответ с исходным AI operation/preset; формы, рестарт, конкурентные квитанции, owner/channel isolation, stale/expired queries, injection и переполнение.

`npm test` запускает регрессии; для PostgreSQL требуется отдельный тестовый сервер через `KIRA_PLATFORM_TEST_PG_PORT`. `npm run test:telegram-widgets` проверяет HTML/JS в изолированном Chromium: 200/320/430/600 px, две темы, страницы и отправку формы без сети. Можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`. Этот тест проверяет DOM/bridge, а не эмулирует нативный renderer Telegram.

`npm run eval:generative-ui -- --live --catalog=v2 --transport=telegram` дополняет тесты решениями настоящей модели на 16 вымышленных сценариях и проверяет размер готового HTML. Личные диалоги и инструменты не используются.

`ts-node scripts/evalUiAnswerPresentation.ts --live` проверяет естественный текст для подписи и озвучки на 10 вымышленных сценариях: без незапрошенных ASCII/Markdown-макетов, с сохранением чисел и с допустимым настоящим программным кодом. `npm run test:telegram-widgets -- --preview=/absolute/path/preview.png` сохраняет визуальный пример из renderer.

Попробовать в обновлённом Telegram:

- «Какая погода сегодня? Покажи прогноз наглядно». Карточка появляется после получения реальных погодных данных.
- «Сравни текущие цены AAPL и MSFT в таблице». Нужны подтверждённые котировки; история цен не выдумывается.
- «Покажи план тренировки по шагам и прогресс». Данные берутся из разрешённых источников обычного диалога.
- «Предложи форму: чтение или прогулка, от 10 до 60 минут с шагом 5, с разминкой или без. После выбора составь план». Кнопка отправляет выбранные значения Кире.
- «Привет» / «Спасибо» / «Просто побудь рядом». Виджет обычно не нужен.
